Security model

What RamDoc protects, how each mechanism works, and where to read about it from a primary source.

RamDoc uses standard, published cryptography rather than anything invented for it. The summaries below are written for a reader who has to trust the application with patient data without reading the code — though the code is there to read, and the references are to the specifications themselves rather than to marketing pages.

Your files are encrypted with AES-256-GCM

AES is the block cipher standardised by the US National Institute of Standards and Technology and used to protect classified information. GCM additionally detects modification, so a file that has been tampered with fails to decrypt rather than returning altered content. A copy of the vault taken off your Mac is unreadable without the key.

NIST FIPS 197 — the AES standard

The database is encrypted too, not just the files

Names, diagnoses and notes are stored in SQLCipher, which encrypts every database page on disk. Opening the file with an ordinary database tool shows random bytes. This matters because metadata — who is a patient at all — is often as sensitive as the notes themselves.

SQLCipher design documentation

Keys are held by macOS, not by the application

Encryption keys are stored in the macOS Keychain, the system service Apple provides for secrets, and are never written to disk in readable form. The application asks the operating system for a key when it needs one and wipes it from memory afterwards.

Apple Platform Security — Keychain data protection

Recovery is a 24-word phrase, derived the slow way

Because there is no company holding a copy of your data, there is no password reset. Instead you get a 24-word recovery phrase in the BIP-39 format used by cryptocurrency wallets, and the key is derived from it with Argon2id — a function deliberately made expensive in time and memory so that guessing the phrase is impractical. Keep the phrase somewhere safe and offline; without it the vault cannot be opened by anyone, including the author of this software.

BIP-39 specification · RFC 9106 — Argon2

The audit log shows if it has been edited

Each audit entry carries a keyed hash (HMAC) computed over the entry before it, so the entries form a chain. Removing or rewriting one breaks every hash after it, and the head of the chain is stored separately in the Keychain — so the tampering is visible even if the whole database file is replaced.

RFC 2104 — HMAC

Search happens inside the encrypted database

Full-text search uses SQLite's FTS5 engine within the encrypted database, so there is no separate plaintext index sitting next to your records — a common way for otherwise-encrypted systems to leak their contents.

SQLite FTS5 documentation

The build itself is pinned

Every step of the automated build refers to third-party code by its exact commit hash rather than a moving tag, which is the practice GitHub recommends against supply-chain attacks: a compromised upstream release cannot silently enter a RamDoc build.

GitHub — security hardening for Actions

Security is a process, not a property. If you find a weakness, please report it privately — the security policy explains how. For the module-level view of where each mechanism sits, see the architecture diagram.
