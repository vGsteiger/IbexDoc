# Translations

RamDoc ships German and English. Both are first-class: a clinician switching
language should never see the other one leak through.

The rule that makes this hold: **views never write user-visible text.** Every
string comes from `src/lib/translations/{de,en}.json` through
`$t('namespace.key')`. A literal in markup pins one language at the call site,
which is what produced the mixed-language UI that `docs/usability-study.md` §14
describes.

`pnpm check:i18n` enforces this and runs in CI. It fails on a hardcoded text
node or user-visible attribute, on any key present in one bundle but not the
other, and on a non-string leaf.

---

## 1. Reading a string

```svelte
<script lang="ts">
  import { t } from '$lib/translations';
</script>

<h1>{$t('patients.title')}</h1>
<Input placeholder={$t('medications.dosagePlaceholder')} />
```

Outside markup — in a `confirm()`, a toast, a `catch` block, a native dialog
title — the store has to be read imperatively:

```ts
import { get } from 'svelte/store';
import { t } from '$lib/translations';

if (!confirm(get(t)('medications.confirmDelete'))) return;
```

Interpolation is `String.replace` on a `{placeholder}` token, because the
bundles are plain JSON:

```svelte
{$t('settings.csvImport.parsed').replace('{rows}', String(preview.total_rows))}
```

## 2. Where a key goes

Domain namespaces mirror the feature: `patients`, `sessions`, `diagnoses`,
`medications`, `reports`, `letters`, `email`, `files`, `literature`,
`treatmentPlans`, `outcomeScores`, `calendar`, `chat`, `settings`,
`onboarding`, `patientHistory`, `errors`, `topbar`, `commandPalette`, `nav`.

`common` is for text that is genuinely shared — `save`, `cancel`, `delete`,
`loading`, `notes`, `back`, `continue`. Reach for an existing key before adding
one: the CSV column mapper in settings labels its target fields from
`patients.*` rather than restating them.

Both bundles are edited together. `check:i18n` fails on drift, so a key added
to one and not the other never reaches `main`.

## 3. Values that are stored, not displayed

Some strings are **persisted data**, and translating them would corrupt
records or break the backend:

| Value | Where it is matched |
| --- | --- |
| `report_type` — `Befundbericht`, `Verlaufsbericht`, `Ueberweisungsschreiben` | the `ReportType` enum in `src-tauri/src/llm/prompts.rs`, string-matched in `llm/tools.rs` |
| `session_type` — `Erstgespräch`, `Verlaufskontrolle`, … | the `allowed_types` whitelist in `src-tauri/src/llm/tools.rs` |
| Treatment plan `status`, goal `status`, `intervention_type` | stable slugs in the database |
| Outcome score `interpretation` — `Minimal` … `Moderately Severe` | computed in `src-tauri/src/models/outcome_score.rs`; the severity styling matches on it |

These keep their stored form in both languages, and only the **display label**
is translated. `src/lib/translations/labels.ts` holds one store per vocabulary:

```svelte
<script lang="ts">
  import { sessionTypeLabel } from '$lib/translations/labels';
</script>

<option value={type}>{$sessionTypeLabel(type)}</option>
```

Every label store falls back to the raw value, which matters because
`session_type` is a free-text field in the session editor and older rows hold
values that were never in any picker. Add the label under the namespace the
store points at, keyed by the stored value — `sessions.types.Erstgespräch`, not
a slug of your own.

## 4. What is not translated

`ALLOW` in `scripts/check-i18n.mjs` is the complete list, and each entry needs a
stated reason. It currently covers language endonyms (`Deutsch`, `Français` —
always written in their own language), the product name, keyboard shortcuts,
input format hints (`756.____.____.__`), example addresses, a model identifier,
and `RESTORE`, the literal word the restore handler string-compares.

Two more categories sit outside the guard because they are not markup:

- **`console.*` messages** are developer-facing and stay English.
- **LLM prompts** — the instruction text sent to the model, e.g. in
  `MedicationChangeAssistant` and `email/new` — are still German regardless of
  UI language, so generated content comes back German in an English UI. Making
  the prompt follow the UI language changes model output and belongs in its own
  change.
